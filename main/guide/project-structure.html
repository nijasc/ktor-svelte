Project structure ​

A project created by the setup script looks like this. Projects that add ktor-svelte to an existing app have the same core: a Gradle build with the plugin, a Ktor app with install(Svelte), and a SvelteKit app in frontend/.

my-app/
  build.gradle.kts            plugins, svelte { } settings, dependencies
  settings.gradle.kts
  gradle/libs.versions.toml   version catalog
  src/main/kotlin/
    Application.kt            embeddedServer, install(Svelte), routes
    Env.kt                    typed access to environment variables
    Errors.kt                 typed error responses
  src/main/resources/
    logback.xml
  frontend/
    package.json
    vite.config.ts            generated by ktor-svelte
    vite.user.ts              your own Vite settings
    src/
      app.html
      routes/                 your pages
      lib/api/                generated TypeScript client
      lib/ktor-svelte/        generated helpers for themes, icons and i18n
    messages/                 i18n message files, if i18n is on
  .run/                       IntelliJ run configurations
  .env.example                every variable the app reads
  Dockerfile                  if you chose Docker

Files you own and files ktor-svelte owns ​

ktor-svelte writes some files for you and keeps them up to date. Each of them starts with a "Generated by ktor-svelte" header. Do not edit them, because the next sync or start overwrites your changes.

FileWritten byChanges when
frontend/src/lib/api/*the app in development, or svelteGenerateTsa route or DTO changes
frontend/vite.config.tssvelteSynclibrary settings change
frontend/src/lib/ktor-svelte/*svelteSyncthemes, icons or locales change
frontend/src/hooks*.tssvelteSynci18n or theme settings change
Kotlin AppTheme and Messages classesthe Gradle build, in build/generated, never committedthemes or messages change

Everything else is yours. ktor-svelte never overwrites a file without the header. If it needs to own a file you already have, such as your own vite.config.ts, the build stops and tells you what to move. Put custom Vite settings in vite.user.ts.

Commit the generated frontend files. A frontend build never needs the JVM app to run first, and svelteVerifyTs and svelteVerifySync in check fail when they are out of date, so a changed DTO cannot drift away from the frontend unnoticed.

The #api import ​

svelteInit and svelteSync add an import alias to frontend/package.json, so pages import the generated client the same way wherever they are:

ts
import { api, isApiError, type Note } from '#api';

What ends up in the JAR ​

svelteBundle copies the static build into ktor-svelte/public/ in your resources and writes ktor-svelte/manifest.json. Hidden files such as .env and source maps are left out. The How it works page explains how requests are answered from the manifest.
