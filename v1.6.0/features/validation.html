On this page

Validation ​

One set of rules for the server and the browser, with errors per field. You write the rules once in Kotlin; the server enforces them on every request, and the generated client checks the same rules in the browser with the same messages.

Ktor plugin Generated client

Quick start ​

Put simple bounds on the properties with Ktor's JsonSchema annotations, and any other rule on the class itself by implementing Validated:

kotlin
import io.ktor.openapi.JsonSchema

@Serializable
data class NoteInput(
    @JsonSchema.MaxLength(80)
    val title: String,
    val body: String = "",
) : Validated {
    override fun Validator.rules() {
        check(::title, title.isNotBlank()) { "A note needs a title." }
    }
}

post("/api/notes") {
    val input = call.receive<NoteInput>()
    call.respond(HttpStatusCode.Created, store.create(input))
}

When something fails, the route never runs, and the client gets a 422 with an error list per field, in one standard shape that isValidationError understands:

json
{ "message": "Validation failed", "fields": { "title": ["A note needs a title."] } }

Where the rules run ​

Both kinds of rule run on every call.receive of that class, in every route:

  • for nested classes, lists, map values and sealed subtypes too
  • for every item when you receive a List or Map of such classes
  • for a query class read with call.query<T>()
  • for the result of a Patch<T>
RuleServerBrowser (validate())
JsonSchema annotationsYesYes, same messages
@Trim, @Lowercase, @EmptyAsNullYesNo, the text is checked as typed
Validated.rules()YesNo, the errors arrive with the 422
validate { } in a routeYesNo, the errors arrive with the 422
fieldCheck routesYesAsked while typing, through formState

Rules on properties ​

AnnotationChecksMessage
@JsonSchema.MinLength(n), @JsonSchema.MaxLength(n)Length of a stringMust be at most 80 characters.
@JsonSchema.Minimum(x), @JsonSchema.Maximum(x)A number, exclusive = true for a strict boundMust be at least 1.
@JsonSchema.Pattern(regex)A string contains a matchMust match ^[a-z]+$.
kotlin
@Serializable
data class Product(
    @JsonSchema.Pattern("^[A-Z]{3}-[0-9]{4}$")
    val sku: String,
    @JsonSchema.Minimum(0.0, exclusive = true)
    val price: Double,
    @JsonSchema.Minimum(1.0) @JsonSchema.Maximum(99.0)
    val quantity: Int,
)

The messages for these bounds are English and are the same in the browser and on the server. For another language, or friendlier wording than Must match ^[a-z]+$., write the rule yourself with check and your own text.

Ready-made rules ​

For the values every app checks, use a preset instead of writing a pattern. Each one has a friendly message, and the server and the browser use the same pattern and the same text:

kotlin
import io.github.nijasc.ktor.svelte.Rule

@Serializable
data class AccountInput(
    @Rule.Email val email: String,
    @Rule.StrongPassword val password: String,
    @Rule.WebAddress val homepage: String? = null,
    @Rule.Phone val phone: String? = null,
    @Rule.Slug val handle: String,
)
AnnotationAcceptsMessage
@Rule.Emailname@example.com: something, @, a domain with a dot, no spacesMust be an email address, such as name@example.com.
@Rule.WebAddresshttp:// or https://, a host with a dot, no spacesMust be a web address that starts with http:// or https://.
@Rule.Phone6 to 20 digits, spaces and + ( ) . / -, such as +49 30 1234567 or (030) 123-45Must be a phone number, such as +49 30 1234567.
@Rule.Sluglowercase letters and digits with single dashes, such as hello-world-2Must be lowercase letters and digits, with single dashes between words.
@Rule.StrongPasswordat least 10 characters with a lowercase letter, an uppercase letter and a digitMust have at least 10 characters, a lowercase letter, an uppercase letter and a digit.
  • A preset checks a value that is there. Combine it with @JsonSchema.MinLength(1) to also refuse an empty text, and make the property nullable to allow leaving it out.
  • In the OpenAPI document each preset is the property's format (email, uri, phone, slug, strong-password); that is how the generated validate() knows which check to run.
  • The patterns are deliberately loose. An email that passes can still bounce; confirm addresses by sending a mail.
  • For your own wording or another language, write the rule with check in Validated.rules() instead.

Rules on the class ​

Anything the annotations cannot say, such as a rule over two fields, goes into Validated.rules():

kotlin
@Serializable
data class Booking(
    val from: String,
    val until: String,
    val guests: Int,
) : Validated {
    override fun Validator.rules() {
        check(::until, until >= from) { "The stay has to end after it starts." }
        check(::guests, guests in 1..8) { "Between 1 and 8 guests." }
    }
}
  • check(::title, condition) { message } adds the message when the condition is false.
  • It names the field from the property, so renaming it in the IDE keeps the error in sync. If the property has a different @SerialName, pass the name as a string instead: check("api_key", ...).
  • Every failed check is collected, so the user sees all problems at once.

Error paths ​

Errors use the JSON name, with paths for nested values:

WherePath

A field of an item in a listlines[1].sku
A field of a map valueprices[eur].amount

Rules inside a route ​

For a rule that depends on the route, such as comparing against a database, call validate { check(...) { ... } } inside the route. It answers the same way, with a 422 and the errors per field:

kotlin
@Serializable
data class CouponInput(val code: String)

post("/api/coupons/redeem") {
    val input = call.receive<CouponInput>()
    validate {
        check("code", input.code.startsWith("WELCOME")) { "That code does not exist." }
    }
    call.respond(HttpStatusCode.NoContent)
}

StatusPages

validate and the other rules throw a ValidationException, which ktor-svelte turns into the 422. If you use Ktor's StatusPages with a handler for all exceptions, it runs first, so let ValidationException through.

Cleaning up input ​

People paste text with spaces around it and type their email address with capitals. Say once, on the field, how it should arrive, and no route cleans up strings by hand:

kotlin
@Serializable
data class SignUp(
    @Trim @Lowercase
    val email: String,
    @Trim
    @JsonSchema.MinLength(1)
    val name: String,
    @Trim @EmptyAsNull
    val company: String? = null,
)
AnnotationWhat arrives in the route
@TrimThe text without whitespace at both ends
@LowercaseThe text in lowercase, independent of the server's locale
@EmptyAsNullnull when the text is empty, which is what a form sends for a field left blank. The property has to be nullable
  • They are applied in that order, so @Trim @EmptyAsNull turns a field of only spaces into null.
  • This happens when the JSON body is received, before the bounds and your Validated rules run, so @Trim @JsonSchema.MinLength(1) refuses a name of only spaces without a rule of your own.
  • On a List<String> or a Map<String, String> they apply to every item or value.
  • They are found in nested classes, in lists of classes, in sealed subtypes with the default type discriminator, and on the property of a value class, so value class Email(@Trim @Lowercase val value: String) is clean wherever it is used.

Server only

Only JSON request bodies are cleaned up, not query parameters, and the browser does not apply them: validate() in the generated TypeScript checks the text as typed. That only matters for a value that is valid after trimming but not before, which the server then accepts.

Sensitive fields ​

The development tools show a lot of what travels between browser and server, and some of it should not be shown: a password, a token, an API key. Mark such a field once:

kotlin
@Serializable
data class Login(
    val email: String,
    @Sensitive
    val password: String,
)

From then on the field's value is replaced by *** wherever ktor-svelte itself displays or stores it:

  • in the curl command the dev panel copies
  • in the fixtures it saves, for request and response bodies
  • in browser console output that is forwarded to the dev log
  • in the request list and the slow call log, for a query parameter of that name

It works for requests and for responses, in nested classes too, and by the JSON name of the field, so @SerialName("api_key") masks api_key.

Two things to know

  • Masking goes by name: once password is marked in one class, every field and query parameter called password is masked in those places, in any class. So give a sensitive field a telling name, not value or next.
  • It changes nothing about your API: the field is received and returned as before. Keeping a value out of a response is still done by not putting it into the response class.

In the browser ​

With generateTs, the same annotations end up in OpenAPI and in the generated TypeScript, so a form gets the bounds without asking the server, and validate() checks a value in the browser with the same messages the server sends:

ts
import { NoteInput } from '#api';

const problems = NoteInput.validate(draft);
const titleBounds = NoteInput.bounds.title;

How bounds and validate() are generated, and which bounds get required, is in Generated TypeScript.

Errors next to inputs ​

use:field puts the bounds on an input and shows its errors right after it, with aria-invalid and aria-describedby set for screen readers. Pass the same errors whether they come from validate() or from a 422:

svelte
<input bind:value={draft.title} use:field={{ bounds: NoteInput.bounds.title, errors: errors.title, errorClass: 'text-error' }} />
OptionWhat it does
boundsThe HTML attributes from bounds, such as maxlength
errorsThe messages for this field. The message disappears when they are empty
errorClassThe class of the message. Defaults to field-error
describedByThe id of the input's own hint, which stays in aria-describedby next to the error

The message is a <p role="alert">.

With libraries { components() }, the generated <Field> wraps this action together with the label and a hint.

Form state ​

Every form needs the same few variables: the values being edited, whether they changed, whether a submit is running, and the errors that came back. formState holds them, so a form is its inputs and one function:

svelte
<script lang="ts">
    import { api, field, NoteInput } from '#api';
    import { formState } from '#lib/api/form-state.svelte.ts';

    const form = formState<NoteInput>(NoteInput.empty(), { validate: NoteInput.validate, resetOnSuccess: true });

    async function create() {
        const note = await form.submit((draft) => api.notes.create(draft));
        if (note) console.log('created', note.id);
    }
</script>

<form onsubmit={(event) => { event.preventDefault(); void create(); }}>
    <input bind:value={form.draft.title} use:field={{ bounds: NoteInput.bounds.title, errors: form.errors.title }} />
    <p role="alert">{form.message}</p>
    <button disabled={form.submitting}>Create</button>
    <button type="button" disabled={!form.dirty} onclick={() => form.reset()}>Discard</button>
</form>
form.draftThe values being edited, deeply reactive, so bind:value={form.draft.title} works
form.dirtytrue while the draft differs from the last saved values
form.submittingtrue while submit waits for the server. A second submit in that time does nothing
form.errorsErrors per field, from validate, from a 422 answer and from checks. Hand them to use:field
form.error, form.messageAny other failure of the last submit, and its text for the user. message is empty when there is none
form.checkingtrue while a check waits for its answer
form.reset()Back to the last saved values, with the errors cleared. form.reset(values) makes values the saved ones, such as after loading a record
form.submitChanges(send)Like submit, but send gets only the changed fields as a Patch<T>, and is not called when nothing changed
form.submit(send)Runs validate first and stops on errors without calling the server. Otherwise calls send with a plain copy of the draft and returns its result, or undefined when it failed
form.conflict, form.takeTheirs(), form.keepMine()After a version conflict: the other person's record, reset to it, or take over its version so the next submit goes through
OptionDefaultWhat it does
validatenoneChecks the draft before sending, such as NoteInput.validate
resetOnSuccessfalseEmpties the form after a successful submit
checksnoneCheck routes per field
checkDelay300Milliseconds of quiet typing before a check is asked
focusErrorstrueAfter a submit that fails validation, in the browser or with a 422, moves focus to the first invalid field
  • After a successful submit the sent values are the saved ones, so the form is no longer dirty. That suits an edit form. For a form that creates something, resetOnSuccess: true empties it again.
  • submit never throws: a failed call ends up in errors or error. The failure still reaches apiConfig.onError, so with toasts on, the user sees it without any markup of yours.
  • The helper uses runes, so it is a module of its own and not part of #api.
  • The draft should be plain data, the kind that goes into a JSON body. dirty compares it as JSON.

What changed ​

Each field knows whether it differs from the saved value. Use it for a marker beside the field, and for a summary of the changes before saving:

svelte
<script lang="ts">
    import Field from '#components/Field.svelte';
</script>

<Field label="Title" bind:value={form.draft.title} changed={form.changed('title')} />

{#if form.dirty}
    <ul>
        {#each form.changes as change (change.field)}
            <li>{change.field}: {String(change.from)} -> {String(change.to)}</li>
        {/each}
    </ul>
{/if}
NameWhat it is
form.changed('title')true while the field differs from the saved value; reactive
form.changesevery changed field as { field, from, to }, in the order of the draft's fields
  • Fields are compared as JSON, so a list or a nested object counts as changed when anything inside it changed, and changing a value back removes it from the list.
  • After a successful submit the sent values are the saved ones, so changes is empty again.
  • <Field changed> shows a small dot after the label, announced as "Changed"; pass a text instead of true for another language, such as changed={form.changed('title') && m.fieldChanged()}.

Send only what changed ​

For a big record where only one field was edited, send just the changed fields. submitChanges validates the whole draft like submit, then calls your function with a Patch<T> of the changed fields only:

svelte
<script lang="ts">
    import { api, NoteInput } from '#api';
    import { formState } from '#lib/api/form-state.svelte.ts';

    const form = formState<NoteInput>({ title: note.title, body: note.body, tags: note.tags }, { validate: NoteInput.validate });

    async function save(event: SubmitEvent) {
        event.preventDefault();
        await form.submitChanges((changes) => api.notes.patch(note.id, changes));
    }
</script>
  • When only the title changed, the body is {"title": "Oat milk"}.
  • When nothing changed, your function is not called and the result is undefined, so a double click on "Save" sends nothing.
  • Fields are compared as JSON against the saved values, the same way as form.changes. A field set to undefined is sent as null, which the server's Patch<T> reads as "clear it".
  • Errors, conflicts and the saved state work exactly as with submit.

Forms in several steps ​

formWizard splits one form into steps. Each step is checked against the same validate() before you can move on, the progress survives a reload, and the whole object is sent once at the end:

svelte
<script lang="ts">
    import { api, Signup } from '#api';
    import Field from '#components/Field.svelte';
    import { formWizard } from '#lib/api/form-state.svelte.ts';

    const wizard = formWizard<Signup>(Signup.empty(), {
        validate: Signup.validate,
        steps: [['name', 'email'], ['company', 'role'], ['password']],
        keep: 'signup'
    });

    async function finish(event: SubmitEvent) {
        event.preventDefault();
        if (!wizard.last) return void wizard.next();
        await wizard.submit((draft) => api.signups.create(draft));
    }
</script>

<p>Step {wizard.step + 1} of {wizard.count}</p>
<form novalidate onsubmit={finish}>
    {#if wizard.step === 0}
        <Field id="name" label="Name" bind:value={wizard.draft.name} errors={wizard.errors.name} />
        <Field id="email" label="Email" bind:value={wizard.draft.email} errors={wizard.errors.email} />
    {:else if wizard.step === 1}
        <Field id="company" label="Company" bind:value={wizard.draft.company} errors={wizard.errors.company} />
        <Field id="role" label="Role" bind:value={wizard.draft.role} errors={wizard.errors.role} />
    {:else}
        <Field id="password" label="Password" type="password" bind:value={wizard.draft.password} errors={wizard.errors.password} />
    {/if}
    {#if !wizard.first}<button type="button" onclick={wizard.back}>Back</button>{/if}
    <button disabled={wizard.submitting}>{wizard.last ? 'Create account' : 'Next'}</button>
</form>
OptionWhat it does
stepsThe fields of each step, in order. Errors of a nested path such as address.city or lines[2].sku belong to the step of address or lines
keepA sessionStorage key. The step and the draft are kept there, so a reload or a back button does not lose the progress; it is cleared after a successful submit or a reset()
validate, checks, focusErrors, ...As for formState
NameWhat it is
wizard.step, count, first, lastWhere you are
wizard.reachedThe furthest step reached; goTo cannot jump past it
wizard.fieldsThe fields of the current step
wizard.next()Checks the current step's fields only; shows and focuses their errors and returns false, or moves on and returns true
wizard.back(), wizard.goTo(n)Move back, or to any step already reached
wizard.submit(send)Checks everything and sends once. When an earlier step is invalid, or the server answers 422 for one of its fields, it jumps back to the first step with an error

Everything else of a formState (draft, errors, dirty, changes, submitChanges, reset, ...) works on the wizard too. form.setErrors(errors) sets the shown errors by hand, on any form.

Focus the first error ​

When a submit fails validation, formState waits for the error messages to appear and then moves focus to the first field marked invalid, scrolled to the middle of the screen. Keyboard and screen reader users land right on the problem, and on a long form nobody has to scroll to find it.

  • It works with every field that uses use:field or the generated components, since they mark invalid fields with aria-invalid="true".
  • It happens for the browser's own validate() and for a 422 from the server alike.
  • Turn it off with focusErrors: false, and call form.focusFirstError() yourself when you want it at another moment.
  • For long forms, add an ErrorSummary above the button: a list of every problem, each a link that jumps to its field.

An edit form ​

For a record that already exists, start with its values and save with update:

svelte
<script lang="ts">
    import { api, field, NoteInput } from '#api';
    import { formState } from '#lib/api/form-state.svelte.ts';

    const form = formState<NoteInput>({ title: note.title, body: note.body, tags: note.tags }, { validate: NoteInput.validate });
</script>

<form onsubmit={(event) => { event.preventDefault(); void form.submit((draft) => api.notes.update(note.id, draft)); }}>
    <input bind:value={form.draft.title} use:field={{ bounds: NoteInput.bounds.title, errors: form.errors.title }} />
    <button disabled={!form.dirty || form.submitting}>Save</button>
</form>

Checks only the server can make ​

Whether an email address is taken, or a coupon code exists, cannot be decided in the browser. Without help, the visitor learns it after sending the whole form. A check route answers the question for one value:

kotlin
import io.github.nijasc.ktor.svelte.fieldCheck

routing {
    fieldCheck("/api/checks/email") { email ->
        if (email == "ada@example.com") "That email address already has an account." else null
    }
}
  • The block gets the value and returns what is wrong with it, or null when it is fine.
  • It runs inside the route, so call is there for the current user or the language.
  • The route is a GET with the value in the value query parameter, never cached, and part of the generated client like any other, such as api.checks.getEmail({ value }).
  • An empty value is never passed to the block, and a value longer than 1000 characters is refused with a 400.

formState asks it while the visitor types:

svelte
<script lang="ts">
    import { api, field, Registration } from '#api';
    import { formState } from '#lib/api/form-state.svelte.ts';

    const form = formState<Registration>(Registration.empty(), {
        validate: Registration.validate,
        checks: { email: api.checks.getEmail }
    });
</script>

<input type="email" bind:value={form.draft.email} use:field={{ errors: form.errors.email }} />
  • The call waits until typing has paused for 300 ms (checkDelay), and an answer that arrives for an older value is dropped.
  • The answer is part of form.errors.email, next to the errors from validate and from a 422, so it shows up the same way with no extra markup.
  • While a check says no, form.submit does not send. form.checking is true while an answer is awaited.
  • An empty value and the value the form started with are not checked. A profile form does not tell its owner that their own email is taken.
  • A check that fails, because the server is unreachable or answers with an error, says nothing. The real answer comes when the form is sent.

Keep the rule in the route

A check does not replace the rule in the route that saves: two people can pass the check at the same moment. Keep the rule there and treat the check as the earlier, friendlier message.

A check route also tells anyone who asks whether a value exists. For email addresses that reveals who has an account, so put the route under a rate limit, as you would the sign-in route.

Full example ​

A registration form: the email is cleaned up and checked while typing, the password is masked in the dev tools, two passwords must match, and the route checks the email once more when the form is sent.

kotlin
@Serializable
data class Registration(
    @Trim @Lowercase
    @JsonSchema.Pattern("^[^@ ]+@[^@ ]+$")
    val email: String,
    @Trim
    @JsonSchema.MinLength(1)
    @JsonSchema.MaxLength(60)
    val name: String,
    @Sensitive
    @JsonSchema.MinLength(12)
    val password: String,
    @Sensitive
    val repeatPassword: String,
    @Trim @EmptyAsNull
    val company: String? = null,
) : Validated {
    override fun Validator.rules() {
        check(::repeatPassword, repeatPassword == password) { "The passwords do not match." }
    }
}

fun Route.registrationRoutes(accounts: Accounts) {
    fieldCheck("/api/checks/email") { email ->
        if (accounts.isTaken(email)) "That email address already has an account." else null
    }

    post("/api/register") {
        val input = call.receive<Registration>()
        validate {
            check(input::email, !accounts.isTaken(input.email)) { "That email address already has an account." }
        }
        val account = accounts.create(input)
        call.toast("Welcome, ${account.name}!", ToastKind.Success)
        call.respond(HttpStatusCode.Created, account)
    }
}
svelte
<script lang="ts">
    import { goto } from '$app/navigation';
    import { api, field, Registration } from '#api';
    import { formState } from '#lib/api/form-state.svelte.ts';

    const form = formState<Registration>(Registration.empty(), {
        validate: Registration.validate,
        checks: { email: api.checks.getEmail }
    });

    async function register(event: SubmitEvent) {
        event.preventDefault();
        const account = await form.submit((draft) => api.register.create(draft));
        if (account) await goto('/welcome');
    }
</script>

<form onsubmit={register}>
    <label>
        Email
        <input type="email" bind:value={form.draft.email} use:field={{ bounds: Registration.bounds.email, errors: form.errors.email }} />
    </label>
    <label>
        Name
        <input bind:value={form.draft.name} use:field={{ bounds: Registration.bounds.name, errors: form.errors.name }} />
    </label>
    <label>
        Password
        <input type="password" bind:value={form.draft.password} use:field={{ bounds: Registration.bounds.password, errors: form.errors.password }} />
    </label>
    <label>
        Repeat password
        <input type="password" bind:value={form.draft.repeatPassword} use:field={{ errors: form.errors.repeatPassword }} />
    </label>
    <label>
        Company (optional)
        <input bind:value={form.draft.company} />
    </label>

    {#if form.message}<p role="alert">{form.message}</p>{/if}
    <button disabled={form.submitting || form.checking}>Create account</button>
</form>

What happens where:

  • In the browser, Registration.validate checks the pattern and the lengths on every submit, and api.checks.getEmail asks about the email while the visitor types.
  • On the server, @Trim @Lowercase clean up the email before anything else, the annotations and rules() run on call.receive, and validate { } checks the email once more, because two people can pass the check at the same moment.
  • Every error lands in form.errors, whichever side found it, and use:field shows it next to the input.
  • The passwords show as *** in the dev panel, the fixtures and the logs.

Use cases ​

  • Any form that sends a body: annotations plus formState.
  • Rules over two fields, such as dates or passwords: Validated.rules().
  • Rules that need the database: validate { } in the route, with a check route for early feedback.
  • Email addresses, names and optional text from forms: cleaning up input.
  • Passwords, tokens and keys: sensitive fields.
  • Two people editing one record: version conflicts.

Good to know ​

  • The 422 has one shape everywhere: { "message": "Validation failed", "fields": { ... } }. isValidationError in the client recognises it.
  • Annotation messages are English. Write a check with your own text for other languages.
  • Write patterns with ^ and $: the browser matches the whole value, the server looks for a match inside it.
  • Classes without annotations or rules are not checked, and get no validate() in TypeScript.
